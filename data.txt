Analyze the complete batch process in this project and create a detailed Markdown file named:

The document must explain the batch from beginning to end in a simple, human-understandable way.

For each rule, provide:

* Output or action
* What happens when the condition is true
* What happens when the condition is false
* Important edge cases
* Any default or fallback behaviour

Do not only explain the technical code. Explain why the business needs the rule.

Use real-life examples with sample data.

Example format:

### Rule: Customer Is Eligible

**Business meaning:**
The customer is processed only when the customer is active and has a valid benefit period.

**Code condition:**

```sql
WHERE CUSTOMER_STATUS = 'A'
  AND CURRENT_DATE BETWEEN START_DATE AND END_DATE
```

**Simple explanation:**
The batch selects only active customers whose benefit period includes today's date.

**Example:**

| Customer   | Status | Start Date | End Date   | Selected? | Reason                             |
| ---------- | ------ | ---------- | ---------- | --------- | ---------------------------------- |
| Customer 1 | A      | 2026-01-01 | 2026-12-31 | Yes       | Active and within the valid period |
| Customer 2 | I      | 2026-01-01 | 2026-12-31 | No        | Customer is inactive               |
| Customer 3 | A      | 2025-01-01 | 2025-12-31 | No        | Benefit period has expired         |

## Documentation Rules

* Analyze the actual code. Do not guess.
* Clearly mark anything that cannot be confirmed from the code.
* Mention exact file names, class names, method names, program names, procedure names, table names, and line numbers where possible.
* Explain technical terms in simple language.
* Expand abbreviations the first time they appear.
* Use tables wherever they improve understanding.
* Use Mermaid diagrams for process flows and table relationships.
* Use realistic sample values.
* Do not skip small methods, helper methods, conditions, or utility functions if they affect the result.
* Follow method calls and dependencies across the whole repository.
* Search for all references to the batch name, job name, table names, status values, and configuration values.
* Separate confirmed behaviour from assumptions.
* If business meaning is not available in the code, state: `Business meaning needs confirmation`.
* At the end, include a section named `Open Questions and Missing Information`.

Before completing the document, verify that it contains:

* End-to-end flow
* Complete business logic
* All important data structures
* Column-by-column explanation
* SQL and `WHERE`-condition explanation
* Real-life examples
* Successful and failure simulations
* Error handling
* Restart logic
* Production-support steps
* Testing scenarios
